# L03 · 按键消抖与状态机

> 日期：2026-11-02 ｜ 目标：把「按键」从"按下去看看"变成可复用的事件源。

## 昨天的做法有什么问题

`01-key-led` 里用 `delay_loops` 消抖：

```c
if (key_pressed()) { delay_loops(400000); if (key_pressed()) { ... } }
```

三个硬伤：

1. **延时长度靠猜**——主频一变（16 MHz → 168 MHz）就完全失效；
2. **阻塞**——消抖期间 CPU 干等，LED 都没法闪；
3. **写不了复杂逻辑**——长按、连发、双击，用 `delay` 会变成意大利面。

## 今天的做法：定时采样 + 状态机

```
每 20 ms 采样一次，根据「上一次状态 + 这次电平」决定迁移
```

```
            ┌──────────┐  按下   ┌──────────────┐  20ms 后仍按下  ┌───────────┐
            │   IDLE   │────────>│ DEBOUNCE_DOWN│────────────────>│  PRESSED  │
            └──────────┘         └──────────────┘                 └───────────┘
                 ^                       │ 20ms 内松开（抖动）           │
                 │                       └──────────────┐               │ 按住 > 1s
                 │                                      │               ▼
                 │        ┌──────────────┐   松开       │       触发 LONG 事件（一次）
                 └────────│DEBOUNCE_UP   │<─────────────┘
                          └──────────────┘
                                 │ 20ms 后仍松开
                                 └──> 触发 SHORT 事件
```

**为什么 20 ms**：机械按键抖动一般 5–20 ms，20 ms 采样一次刚好把抖动"跨过去"。

**为什么短按在松开时判定**：按下瞬间还不知道用户要按多久，只有松开才能确定"这是短按"。

## 关键代码

```c
typedef enum { KEY_IDLE, KEY_DEBOUNCE_DOWN, KEY_PRESSED, KEY_DEBOUNCE_UP } key_state_t;
typedef enum { KEY_EVT_NONE, KEY_EVT_SHORT, KEY_EVT_LONG } key_event_t;

key_event_t key_scan(key_t *k, uint32_t now_ms);   // 每 20 ms 调一次
```

主循环：

```c
if ((now - last_scan) >= 20) {
    last_scan = now;
    handle_event(key_scan(&key_pa15, now));
    handle_event(key_scan(&key_pe6,  now));
}
/* LED 更新与按键扫描互不阻塞 */
```

## 现象

| 操作 | 结果 |
| --- | --- |
| 短按 | 模式循环：灭 → 常亮 → 慢闪（0.5 s）→ 灭 |
| 长按 1 秒 | 立刻熄灭（不等松手） |

## 踩坑

1. **PA15 复位后是 JTDI**。`MODER` 设成输入即当普通 GPIO 用，不影响 SWD（PA13/PA14）。按它没反应就改用 PE6。
2. **上拉必须开**。按键一端接 GND，不配上拉会读到浮空值。
3. **松开也要消抖**。松开瞬间同样有抖动，所以有 `DEBOUNCE_UP` 状态。
4. **长按只触发一次**。用 `long_sent` 标志，否则按住会疯狂触发。

## 自测三题

1. 为什么消抖不能只在「按下」时做，还要在「松开」时做？
2. 如果把采样周期从 20 ms 改成 5 ms，会出什么问题？改成 100 ms 呢？
3. `key_scan` 为什么必须每 20 ms 调一次，而不是"有空就调"？如果主循环卡了 500 ms 会怎样？

<details><summary>参考答案</summary>

1. 松开也有 5–20 ms 抖动，不消抖会误判成"又按了一下"，短按事件会重复触发。
2. 5 ms 可能还在抖动区，容易误判；100 ms 会漏掉短按（人快速点击约 80–150 ms）。
3. 状态机靠 `now_ms` 推进，调用间隔不稳定会导致长按判定不准；主循环卡住会丢采样，按键事件丢失。

</details>

## 顺带说清楚：这和 RTOS 的关系

FreeRTOS 里也是这个套路：任务里 `xQueueReceive(..., 20ms)` 拿到"扫描事件"，再喂给状态机。区别只是"每 20 ms"由定时器队列提供，而不是 `g_ms`。今天写的状态机，明天搬到 RTOS 里几乎不用改。
